# V19 · L20–22 — Memory Basics and Contiguous Allocation: Where Does a Process Live?

> **Lecture:** CS502 L20 `20-memory-management-background` + L21 `21-contiguous-allocation` + L22 `22-allocation-strategies-fragmentation` · **Unit:** III · **Target length:** 16–18 min · **Series position:** 19/28
> **Format:** screen-capture animation (memory bar + MMU) · **Language:** English (Hinglish version optional)

## 1. Why this deserves a video

This video opens the memory unit, and almost everything in it moves: addresses being rewritten
on their way to RAM, processes being swapped out to disk, holes appearing and splitting as jobs
come and go, and memory being shuffled during compaction. A static slide shows one snapshot of a
memory bar; students then cannot tell first, best and worst fit apart because the *difference*
only shows up after several requests. Running all three strategies on the same hole list, side
by side, shows the key surprise: two of them refuse a request even though plenty of memory is
free in total. That is external fragmentation, and it motivates paging in V20.

## 2. Learning outcomes

After watching, the student can:
- [Remember] Describe the resident monitor and the three times at which addresses can be bound (compile, load, execution).
- [Apply] Translate a logical address to a physical address with a relocation register and a limit register, or detect the trap.
- [Understand] Explain dynamic loading, dynamic linking and swapping, and why each saves memory.
- [Apply] Allocate a request sequence with first fit, best fit and worst fit on a given hole list, and report the remaining holes.
- [Analyze] Distinguish internal from external fragmentation, compute each in an example, and explain compaction and the 50-percent rule.

## 3. Prerequisites

- Basic computer fundamentals: RAM as an array of numbered bytes, an address, KB as a unit, a program file on disk.
- V01–V02: the OS as resident software; kernel vs user mode; traps (an error raises a trap into the OS).
- V05: a process and its PCB, which records memory limits.
- V06: context switch; the dispatcher loads registers for the next process.
- V08–V09: scheduling (only to know that many processes are in memory at once).

## 4. Hook (first 30–45 s)

A memory bar labelled 0 to the top. Five free gaps of different widths, shaded green, between
grey occupied blocks. A counter at the side: "Free memory: 980 KB".

> "This machine has 980 KB free. A new program arrives and needs 420 KB. Easy, right?
> (Red flash: REQUEST REFUSED.)
> The OS said no. Not because memory is full, but because the free memory is in the wrong
> *shape*. By the end of this video you'll know exactly why, which placement rule caused it,
> and which one would have said yes."

## 6. Worked example (verified)

**A. MMU with relocation and limit registers.** Relocation = 14000, limit = 3000.

| Logical | `logical < limit`? | Physical |
|---|---|---|
| 0 | yes | 14000 |
| 346 | yes | 14346 |
| 2999 | yes | 16999 |
| 3000 | no | **trap** |
| 3500 | no | **trap** (checkpoint 1) |

**B. MFT.** Partitions 100, 200, 300, 400 KB; processes A 90, B 250, C 120, D 380 KB; each process
goes to the smallest free partition that fits.

| Process | Size | Partition | Internal fragmentation |
|---|---|---|---|
| A | 90 | 100 | 10 |
| B | 250 | 300 | 50 |
| C | 120 | 200 | 80 |
| D | 380 | 400 | 20 |

Total internal fragmentation **160 KB**.

**C. First / best / worst fit.** Holes in address order H1–H5 = 150, 450, 250, 350, 550 KB
(total 1750). Requests in order: P1 230, P2 400, P3 140, P4 420 KB. A hole is split; the leftover
stays in place.

*First fit*

| Request | Hole chosen | Holes after (H1…H5) |
|---|---|---|
| P1 230 | H2 (450) → 220 left | 150, 220, 250, 350, 550 |
| P2 400 | H5 (550) → 150 left | 150, 220, 250, 350, 150 |
| P3 140 | H1 (150) → 10 left | 10, 220, 250, 350, 150 |
| P4 420 | **none ≥ 420 → waits** | 10, 220, 250, 350, 150 |

Free 980 KB, largest hole 350 KB: **P4 refused** (external fragmentation).

*Best fit*

| Request | Hole chosen | Holes after |
|---|---|---|
| P1 230 | H3 (250) → 20 left | 150, 450, 20, 350, 550 |
| P2 400 | H2 (450) → 50 left | 150, 50, 20, 350, 550 |
| P3 140 | H1 (150) → 10 left | 10, 50, 20, 350, 550 |
| P4 420 | H5 (550) → 130 left | 10, 50, 20, 350, 130 |

All four placed; free 560 KB, largest hole 350 KB.

*Worst fit*

| Request | Hole chosen | Holes after |
|---|---|---|
| P1 230 | H5 (550) → 320 left | 150, 450, 250, 350, 320 |
| P2 400 | H2 (450) → 50 left | 150, 50, 250, 350, 320 |
| P3 140 | H4 (350) → 210 left | 150, 50, 250, 210, 320 |
| P4 420 | **none ≥ 420 → waits** | 150, 50, 250, 210, 320 |

Free 980 KB, largest hole 320 KB: **P4 refused**.

Checkpoint 2: holes 80, 300, 160, 220; request 150 → first fit **300**, best fit **160**, worst fit **300**.

**D. Compaction.** Memory 0–1000 KB: OS 0–100, P1 100–300, hole 300–400 (100), P2 400–650,
hole 650–800 (150), P3 800–950, hole 950–1000 (50). Free total **300 KB**, largest hole
**150 KB**. Compaction: P2 (250 KB) moves to 300–550, P3 (150 KB) to 550–700; single hole
**700–1000 = 300 KB**. Data copied: 250 + 150 = **400 KB**.

**E. 50-percent rule.** N = 1000 allocated blocks → about 0.5 × 1000 = **500** blocks lost;
fraction unusable 0.5 / 1.5 = **1/3**.

## 8. Misconceptions to address on screen

- "The MMU adds the base first, then checks the limit against the physical address." → Scene 6: the limit is compared with the *logical* address, before adding; label the comparator "logical < limit".
- "A program knows its physical addresses." → Scene 5: the CPU and program see only logical addresses.
- "Best fit is always best." → Scene 11 caveat: it wins on this sequence; in general first fit and best fit are similar in storage use and first fit is faster; best fit leaves many tiny holes (10, 50, 20 here).
- "Internal fragmentation happens in variable partitions." → Scene 15: MFT → internal; MVT → external.
- "Compaction is always possible." → Scene 13: only with execution-time binding; with compile- or load-time binding processes cannot move.
- "The 50-percent rule means half of memory is wasted." → Scene 14: half as many *blocks* as allocated ones are lost, which is one-third of memory.
- "Dynamic loading needs special OS support." → Scene 8: dynamic loading is up to the program; dynamic linking needs OS help.

## 11. End-of-video quiz

1. **(Numerical)** Relocation register = 5200, limit register = 1800. Give the physical address for logical 1799, and state what happens for logical 1800. **Answer: 6999; trap.**
2. **(MCQ)** Holes (in order) 80, 300, 160, 220 KB; request 150 KB. Which hole does best fit choose?
   (a) 80 (b) 300 (c) 160 (d) 220
   **Answer: (c).**
3. **(Numerical)** Memory has fixed partitions of 64 KB each. Four processes of 40, 64, 10 and 33 KB are loaded, one per partition. Total internal fragmentation? **Answer: 109 KB.**
4. **(MCQ)** Which binding time allows a process to be moved during execution, making compaction possible?
   (a) compile time (b) load time (c) execution time (d) link time
   **Answer: (c).**
5. **(Short answer)** Free memory is 600 KB in four holes, the largest 200 KB; a 250 KB request fails. Name the problem and two remedies. **Answer:** external fragmentation; compaction, or non-contiguous allocation (paging/segmentation).

**Viewer questions to expect in comments** (answers for a pinned reply):

- Does Linux use relocation and limit registers today? No; it uses paging (V20), but the logical-vs-physical idea is the same.
- Is worst fit ever used? Rarely; simulations favour first and best fit.
- Can compaction run while processes execute? Only if they can be moved, i.e. execution-time binding, and it pauses the moved processes.
